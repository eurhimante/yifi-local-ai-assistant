# YIFI v0.3.1 — Web Tools and Source Provenance

**Status:** Deployed and smoke-tested in the LibreChat environment (October 24, 2026)  
**Conversational model:** `yifi:4b` (Ollama)  
**Git revision:** `6891adc` on `feature/web-search` (reported pushed to GitHub)

## Overview

YIFI v0.3.1 extends the local FastAPI router from a single-model chat proxy into a **bounded, read-only tool orchestration layer**. It lets the local model request SearXNG searches and retrieve the latest published stable release metadata for a GitHub repository using GitHub's REST API.

The main improvement over the initial web-search prototype is **server-side source provenance**: successful and failed GitHub tool calls are recorded in the final response by the router rather than relying solely on what the language model says it did.

## What this release adds

| Capability | Behavior |
| --- | --- |
| Single conversational model | Continues to route requests to `yifi:4b`; exposes `yifi-auto` to LibreChat. |
| `web_search` | Queries the existing SearXNG service for titles, URLs, and short snippets (up to five results). |
| `github_latest_release` | Queries the GitHub REST `releases/latest` endpoint and returns repository, tag, publication date, and release URL on success. |
| Tool orchestration | Runs model-requested tools through FastAPI, with a limit of three tool calls per request. |
| Tool provenance | Appends a server-generated *Tools actually executed* section when applicable, including GitHub verification success or failure. |
| False-verification guard | Adds a tested safeguard against some unsupported model claims of GitHub/API verification when no tool was executed. |
| LibreChat compatibility | Retains `/health`, `/v1/models`, `/v1/chat/completions`, and OpenAI-compatible server-sent events for `stream=true`. |

## Architecture

```text
LibreChat (yifi-auto)
       |
       v
FastAPI router :8001
       |
       +--> Ollama / yifi:4b
       |       |
       |       +--> Requests tool calls
       |
       +--> Tool orchestrator (max 3 calls)
                |
                +--> web_search --> SearXNG --> public-web snippets
                |
                +--> github_latest_release --> GitHub REST API
       |
       v
Model response + server-generated provenance (when tools execute)
```

The development setup uses a separate `yifi-router-dev` container on `127.0.0.1:8002`; the production router remains a distinct container. Both share the existing Ollama and SearXNG services.

## Verified behavior

Validation performed during development:

- **5 automated unit tests passed**, including normal conversation, advertised tool availability, and guards for unsupported API-verification claims in French/English.
- **3 development integration scenarios passed** against the live model: basic conversation, successful `ollama/ollama` GitHub lookup, and a nonexistent repository returning a failed verification.
- **SSE compatibility passed:** a `stream=true` request returned HTTP 200, `text/event-stream`, assistant message chunks, and a final `data: [DONE]` event.
- **Production rollout passed the `/health` check** with `{"status":"ok","model":"yifi:4b"}`. A production LibreChat request returned the GitHub tool's server-generated verification trace.

Example of a successful GitHub lookup observed in testing:

```text
github_latest_release: GitHub API confirmed ollama/ollama v0.40.10
(2026-10-23T15:03:59Z)
```

This example is a **historical test result**, not a live assertion of the current latest version.

## Known limitations

1. **Web searches only provide snippets.** YIFI cannot yet fetch and read arbitrary page contents; `web_fetch` is planned for v0.3.2.
2. **Tool selection is model-driven.** `yifi:4b` may decline to invoke a tool, even when verification would help. The false-provenance guard does not guarantee every inaccurate or misleading statement is detected.
3. **Generated commentary can still be wrong.** In a production test, the model described a GitHub-provided publication date as “simulated” despite the verified server trace. Structured facts should eventually be formatted by the router when appropriate.
4. **Streaming is SSE-compatible but buffered.** The orchestrator completes its tool cycle before emitting the final response; it does not yet provide full token-by-token generation during tool use.
5. **SearXNG availability depends on search engines.** Some engines encountered CAPTCHAs and HTTP rate limits; results may be incomplete.
6. **No personal memory or document RAG yet.** PostgreSQL/pgvector-based features are future work.
7. **No general-purpose page reader yet.** Any future URL-fetching tool must block private/local networks and unsafe redirects to protect homelab services.

## Security and operational choices

- Tools are read-only and explicitly allowlisted.
- Arguments are validated by the tool implementations.
- Search-result text is treated as untrusted input, not executable instructions.
- A tool-call budget limits runaway loops.
- Changes are developed and tested in a separate container before deployment.
- A timestamped production/development source backup was created before rollout. Backups described here cover the router source, not all LibreChat data or secrets.

## Next steps

**v0.3.2:** Add secure web-page fetching, better source selection, and clearer distinctions between search snippets, fetched pages, and structured API verification. Continue development and integration testing outside the production router.

**v0.4:** Introduce explicit, user-controlled personal memory backed by PostgreSQL, followed by document retrieval/RAG in a later phase.
